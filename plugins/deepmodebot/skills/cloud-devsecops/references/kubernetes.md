# Kubernetes operations and ecosystem routing

Read when the task involves kubectl, kubeconfig contexts, namespaces, manifests, Pods/controllers, cluster rollouts, Services/DNS/Ingress/Gateway API, PVCs, Kubernetes authorization, GitOps, or cluster observability. Reviewed 2026-11-13. Vendor facts are cited inline; routing rules, goals and stop caps below are **deepmodebot recommendations**, not Kubernetes defaults. Full selection rationale and source manifest: [Kubernetes ecosystem research](https://github.com/TimothyVang/deepmodebot/blob/main/docs/research/kubernetes-ecosystem.md).

Security hardening, supply-chain verification and pipeline gates remain in [devsecops-pipeline.md](devsecops-pipeline.md); consult that reference for policy changes rather than duplicating its checklist. Managed-cloud identity/networking also routes to the relevant `aws.md`, `azure.md` or `gcp.md` reference.

## First choose the boundary

| Task signal | Route and evidence to obtain | Completion boundary |
|---|---|---|
| Image build, local container process or Compose failure | Container workflow first; Kubernetes only if scheduling, cluster configuration or traffic changes the failure | Same image/application oracle, not a cluster migration |
| kubectl cannot find workload; wrong environment | Trusted kubeconfig, explicit context, namespace and object identity | Intended cluster/namespace established without switching global defaults |
| YAML/chart/overlay authoring | Existing Helm or Kustomize convention; render and inspect desired objects | Artifact validation only until separately authorized runtime checks |
| Pending, CrashLoopBackOff, OOMKilled, failed probe | Workload owner → Pod status/events → selected container logs → resources/configuration | Original failure explained and, if authorized, original oracle passes |
| Service unreachable, DNS/Ingress/Gateway failure | Client namespace → DNS → Service selector/ports → EndpointSlices → readiness → controller/network policy | Same client path, hostname/protocol and response contract pass |
| PVC pending, mount failure, stateful rollout | PVC/PV binding, StorageClass/CSI and topology; application durability contract | Binding/mount plus application data check; no destructive reset |
| Deployment or GitOps rollout | Owner/reconciler, intended revision/digest, rollout status and application oracle | Both control-plane convergence and user-visible health |
| RBAC denial, admission rejection, network isolation | Narrow denied action/policy/CNI evidence; security reference | Scoped fix with positive and negative checks, not wider permissions |
| Capacity, autoscaling, latency or telemetry | Existing Metrics Server, Prometheus or OpenTelemetry deployment | Correct signal at intended backend with original latency/error oracle |

## Safety contract and bounded loop

1. **Scope before access.** Record trusted kubeconfig source, context, cluster identity, namespace, object kind/name, environment, owner, and allowed operations. Contexts combine cluster/user/namespace; `--context` overrides current context. Untrusted kubeconfig can execute code or expose files. Prefer explicit command flags to changing current context. Namespaces do not scope Nodes, PVs, StorageClasses or other cluster-scoped resources. ([kubeconfig](https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/), [namespaces](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/))
2. **Preserve the oracle.** Record the original failing request/test, client location, expected result, revision/digest, latency/error threshold, observation window and allowed data effects. Keep these fixed across attempts. A weaker probe, deleted test or larger deadline is not evidence of a fix. A changed oracle needs explicit approval and separate rationale.
3. **Read-only evidence first.** Once cluster reads are authorized, use scoped `get`, `describe`, events and selected container logs; redact credentials and sensitive payloads before sharing. Bound logs by time/tail and API requests by timeout. Start at the named resource and its owner; expand namespace/cluster scope only when evidence requires it. Avoid broad Secret dumps or raw kubeconfig output. `exec`, `debug`, port forwarding and synthetic requests are separate active operations, not passive inspection.
4. **One hypothesis, one authorized change.** Explain expected observation and rollback conditions before a mutation. Follow the existing controller/GitOps source of truth: live patches can be reconciled away. Publishing desired-state changes, sync/prune, upgrades, restarts, scaling, policy edits and rollback can all affect production. Require explicit production approval covering exact context, namespace, targets, diff, data risk and rollback; research permission grants none of these. No blanket roles, namespace deletion, forced conflicts, finalizer removal or PVC deletion to make a check green. ([reconciliation](https://kubernetes.io/docs/concepts/overview/working-with-objects/), [Flux drift example](https://fluxcd.io/flux/get-started/))
5. **Use finite caps.** Set a task wall-clock limit, maximum diagnostic rounds, mutation budget and per-command timeout before starting. Suggested initial investigation cap: three evidence/hypothesis rounds, ten minutes, zero mutations without approval; an approved repair gets one change then the agreed verification window. Adapt caps to the workload before the run, never silently reset them. Stop on cap, scope/identity mismatch, concurrent revision change, permission denial, unexpected data risk or worsening health; return evidence and the exact blocked decision. Do not retry denied access by escalating privileges.
6. **Finish with two results.** Report rollout/convergence status separately from application behavior, and report `passed`, `failed` or `not observed` for each. No cluster access means a manifest review cannot become a deployment-success claim. Preserve the original failure and commands/output references even if rollback was approved.

Illustrative read-only commands below require confirmed `CTX`, `NS`, `POD`, `CONTAINER`, `WORKLOAD` and `REVISION`; they were not executed during this research. Shell variable syntax is illustrative, not portable to every shell.

```sh
kubectl --context="$CTX" --namespace="$NS" --request-timeout=15s get deployment "$WORKLOAD"
kubectl --context="$CTX" --namespace="$NS" --request-timeout=15s describe pod "$POD"
kubectl --context="$CTX" --namespace="$NS" --request-timeout=15s logs "$POD" -c "$CONTAINER" --since=10m --tail=200
kubectl --context="$CTX" --namespace="$NS" --request-timeout=15s rollout status "deployment/$WORKLOAD" --revision="$REVISION" --timeout=120s
```

For a restarted container, the corresponding `logs --previous` is a separate bounded evidence request. Pin the Deployment revision: by default `rollout status` follows the latest rollout even if another starts; timeout zero means unlimited. A successful rollout is not a business-transaction assertion. ([rollout status](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_rollout/kubectl_rollout_status/))

## Kubernetes facts that change decisions

| Concern | Fact and operational consequence |
|---|---|
| Desired state | Objects express intent in `spec`; controllers report observed state in `status` and reconcile. Change the owning workload/source, not a replaceable Pod. ([objects](https://kubernetes.io/docs/concepts/overview/working-with-objects/)) |
| Workload choice | Deployment: interchangeable stateless Pods. StatefulSet: stable identity/storage association, not an application replication/backup implementation. DaemonSet: node-local facilities. Job/CronJob: completion/schedule. ([workloads](https://kubernetes.io/docs/concepts/workloads/)) |
| Batch work | Job `backoffLimit` bounds retries and Job-level `activeDeadlineSeconds` bounds execution; the latter takes precedence. CronJobs can create duplicate or miss executions, so use idempotent processing and explicit concurrency/deadline decisions. Completion also needs the intended output/data oracle, not merely an exit code. ([Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/), [CronJobs](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)) |
| Probes | Startup gates readiness/liveness until success; readiness governs normal Service traffic eligibility; liveness can restart containers. Poor liveness checks can cause cascading failures. Do not convert a dependency outage into repeated restarts or loosen probes solely to pass rollout. ([probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)) |
| Resources | Requests inform scheduling; CPU limits throttle and memory limits can lead to OOM kills. Check requests/limits, termination evidence and workload demand before increasing resources. A Pending Pod is not automatically an image problem. ([resources](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)) |
| Service and DNS | Service selectors normally determine backing endpoints represented by EndpointSlices. Short DNS queries depend on the caller's namespace; cross-namespace lookup must name it. Cluster domain is configurable, not always `cluster.local`. DNS resolution does not establish healthy endpoints or authorized connectivity. ([Service](https://kubernetes.io/docs/concepts/services-networking/service/), [DNS](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)) |
| Ingress/Gateway | Ingress handles HTTP(S), needs a controller, and its API is frozen; Kubernetes recommends Gateway for new capabilities. GatewayClass identifies shared controller behavior, Gateway requests listeners, Routes map traffic to Services. Gateway API needs installed CRDs and a matching implementation; inspect its supported features and route attachment constraints rather than treating API presence as working traffic. Preserve existing Ingress unless migration is requested. ([Ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/), [Gateway model](https://gateway-api.sigs.k8s.io/docs/concepts/api-overview/)) |
| Configuration | ConfigMap is nonconfidential. Environment-variable consumers do not automatically refresh; `subPath` mounts do not receive ConfigMap updates. Mounted-file refresh alone does not prove the application reloaded it. Secret is not encryption: Kubernetes defaults to unencrypted etcd storage; Pod-creation privileges can expose namespace Secrets. Check actual encryption/RBAC, never print values as routine evidence. ([ConfigMap](https://kubernetes.io/docs/concepts/configuration/configmap/), [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/)) |
| Storage | PVC requests bind PVs; dynamic provisioning depends on StorageClass/provisioner. `Delete` reclaim policy can remove backing storage. Bound/Ready is not backup, restore or application durability proof. Investigate binding, topology and mount events; changes involving persistent data need a separate approval and recovery plan. ([persistent volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)) |
| RBAC | Permissions are additive, with no deny rules. RoleBinding can scope a ClusterRole's namespaced permissions to one namespace; ClusterRoleBinding grants cluster-wide. Fix the minimum required verb/resource/scope, not `cluster-admin`. ([RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)) |
| Pod Security | `warn` and `audit` allow violations; `enforce` rejects Pods. Enforcement does not reject the Deployment template itself, so Deployment dry-run acceptance can coexist with later rejected Pods. Exemptions bypass checks. Use the security reference for rollout policy. ([Pod Security Admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/)) |
| NetworkPolicy | Requires an enforcing network plugin; policies allow traffic additively and ingress/egress isolation are independent. Standard NetworkPolicy is L3/L4, not TLS/authentication or application-layer policy. DNS egress must be considered. Host traffic, `hostNetwork`, existing connections and implementation timing have caveats; API acceptance does not prove isolation. Verify allowed and denied flows from intended clients only with authorization. ([NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/)) |

## Tool selection without adding a platform

These are **recommendations**; retain an existing supported choice unless a documented requirement fails.

- **Local cluster:** [kind](https://kind.sigs.k8s.io/) for disposable Kubernetes testing/CI; [k3d](https://k3d.io/stable/) when K3s-in-Docker is intentionally representative; [minikube](https://raw.githubusercontent.com/kubernetes/minikube/master/README.md) for interactive local development and its addons. None proves managed-cloud load balancing, IAM, CNI or CSI parity. Cluster creation is a separate authorized action.
- **Packaging:** [Helm](https://helm.sh/docs/intro/using_helm/) for chart/release distribution; [Kustomize](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/) for composing manifests and environment patches. Render the selected values/overlay, then inspect resulting names, namespace, images and privileges. Do not add both without a real ownership need.
- **GitOps:** [Argo CD](https://argo-cd.readthedocs.io/en/stable/) when application-centric sync/diff/health UI is useful; [Flux](https://fluxcd.io/flux/get-started/) for controller-driven Git reconciliation using its resource model. Do not let competing reconcilers own the same resources. Sync/Ready is not the original application oracle.
- **Observability:** [Metrics Server](https://kubernetes-sigs.github.io/metrics-server/) supplies autoscaling/resource metrics and `kubectl top`, not a historical monitoring system. [Prometheus](https://prometheus.io/docs/introduction/overview/) supplies time-series collection/query/alerts. [OpenTelemetry Collector](https://opentelemetry.io/docs/collector/) receives/processes/exports traces, metrics and logs to a backend; its [Kubernetes Operator](https://opentelemetry.io/docs/platforms/kubernetes/) manages collectors/auto-instrumentation. They are complementary, not interchangeable installation prerequisites.
- **Additional policy:** [Kyverno](https://kyverno.io/docs/introduction/) offers declarative validation/mutation/generation/image-policy and CLI workflows; [Gatekeeper](https://open-policy-agent.github.io/gatekeeper/website/docs/) integrates OPA-backed admission and audit. Prefer existing organizational policy expertise; check installed API versions and exception scope. Refer to [pipeline policy guidance](devsecops-pipeline.md) for security gates. Audit success is not enforcement proof; never disable admission to achieve rollout success.

## Evidence ladder

1. **Local render:** `helm template` or `kubectl kustomize` produces proposed objects, not a running system. Helm documents that local lookups are faked and server-side API support validation is absent. ([Helm template](https://helm.sh/docs/helm/helm_template/), [Kustomize](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/))
2. **Client dry-run/schema check:** `kubectl apply --dry-run=client` prints the would-be object without submitting it for persistence; do not assume every client validation path is offline or that the target has the APIs. ([apply](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_apply/))
3. **Server dry-run:** requires authorized access to the explicit cluster and the same authorization as a real request; evaluates admission/defaulting/schema/merge without persistence. It is not a read-only RBAC fallback and does not schedule Pods, pull images or exercise downstream controllers. ([API dry-run](https://kubernetes.io/docs/reference/using-api/api-concepts/#dry-run))
4. **Runtime evidence:** after separately approved deployment, observe the exact revision, Pod readiness, dependencies, traffic path and original application oracle for a finite window. Local-cluster success supports that environment only. Missing runtime access remains `not observed`, not inferred success.
