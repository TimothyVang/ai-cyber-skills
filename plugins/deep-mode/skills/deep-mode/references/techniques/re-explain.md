# re-explain

**Use when:** the user signals your last message did not land: "wait, what?", "I'm lost", "huh", "say that again simply", "too dense", "explain like I wasn't here". Restating the *user's* goal is **in-your-own-words** (`references/techniques/in-your-own-words.md`); explaining code they want to learn is **teach**. This technique re-pitches *your* message.

1. **Find the point.** Reread your last message and name the one thing the user must take from it: a result, a decision you made, or something you need from them. Everything else is support or cut.
   Done when you can state the point in one sentence.
2. **Give the missing context first**, in one or two sentences: what we were doing and where it stands now. Assume they skimmed or stepped away.
3. **Restate the point** in Simplified Technical English:
   - Short sentences: up to 20 words for steps, 25 for descriptions. One idea per sentence.
   - Active voice, present tense. Name who does what.
   - Common words with one meaning each. Use the same word for the same thing every time.
   - The project's terms from `GLOSSARY.md` when it exists; never a synonym for a glossary term. Define any other technical term in plain words on first use.
   - Steps as a numbered list, one action per step.
   - No new content. Drop the detail that buried the point; offer it at the end instead.
4. **Use a different form** from the first attempt: a concrete example, a before and after, a small table, or a short diagram where structure was the problem. Never the same paragraph with fewer words.
5. **End with what you need from them**, if anything, as one direct question. Otherwise end on the point.
   Done when the message ends on one question or on the point.

**Hard rules.** Shorter than the original. No apology or preamble ("Let me clarify"). No machinery in the reply (SKILL.md "Writing the reply").

**Output:** the re-pitched message only.

**Done when** the new message is shorter than the original, uses a different form, and states the point.
